Decisions made (recorded so they are not re-litigated):

- **Rejected the literal handoff “pre-post identity guard” in the bridge hot path.** The bridge never reposts: the claim (`CLAIM_INBOUND_DECISION` / `DECIDE_OUTBOUND_MIRROR_CLAIM`) returns 202/503 for any existing row and the order stays `claim → 202 → post → finalize`. A duplicate GHL post is therefore impossible without an uncommitted claim. Adding a blocking, itself-failable GHL read before posting adds latency and new failure modes for no gain. **The reconciler is the safety net:** a lost/timed-out post leaves `processing`/`failed`, and the reconciler proves it via `altId == Unipile message_id` or holds it.
- **Rejected moving the event claim before contact resolution.** The only orphan window (between shared profile-claim acquisition and index/map write) is already tracked by the pending `linkedin_contact_profile_claims` row; a retry fails closed and cannot create a second contact. Restructuring the live 58-node bridge without live validation is riskier than the gap it would close.

## Findings

1. **High — acknowledged inbound/outbound mirror messages can be lost.** The bridge sends HTTP 202 immediately after the event claim, then posts to GHL. If the HTTP node errors, n8n stops after the acknowledgement and the event remains `processing`; if GHL returns a non-2xx response, the row becomes `failed`. In either case, `CLAIM_INBOUND_DECISION` and `DECIDE_OUTBOUND_MIRROR_CLAIM` return HTTP 200 `duplicate` for any existing claim regardless of `processing` or `failed`. A webhook retry therefore does not repost it. The schema has retry indexes but no retry/reconciliation workflow. Repair needs a durable queue/reconciler that checks GHL for an already-created message before retrying, so a timeout cannot create duplicates.
2. **High — GHL-to-Unipile send can become permanently uncertain.** Gateway claims the GHL message ID before calling Unipile. If Unipile sends but the HTTP call or subsequent ID capture/ledger update fails, the claim stays `processing`; repeat callback returns `outbound_send_reconciliation_required` and does not send again. This correctly avoids duplicate LinkedIn sends, but there is no automated reconciliation against the Unipile chat. The earlier 401 test required manual reconciliation; the same gap remains for future failures.
3. **Medium — text-only bridge silently omits non-text inbound events.** `Verify HMAC + Allowlist` rejects `message.new` when `payload.text` is absent/blank, and the GHL outbound validator explicitly rejects attachments. That is safe for current text verification but means attachment-only, media, and some rich Sales Navigator events will not appear bidirectionally. The signed webhook receives HTTP 400 for such events. Confirm product scope, then implement attachment validation, transport, and idempotency if these must sync.
4. **Medium — GHL `altId` uses the chat ID for every mirrored message.** The current code posts `altId` as the Unipile chat ID for both inbound and external outbound messages. HighLevel documents `altId` as the external provider's *message* ID. Reusing a chat ID obscures per-message identity and may affect threading or duplicate reconciliation. Preserve chat routing through the separate map and store the Unipile message ID in `altId` after verifying how GHL returns `replyToAltId` for this provider.
5. **Low — contact/chat recovery is conservative but manual.** Existing chat maps take priority over the current GHL profile index. This protects the tested thread from ambiguous contacts, but a stale/wrong map will continue to route to its saved contact until manually reconciled. Profile claims deliberately never auto-expire after a create attempt. There are no pending claims or conflicting maps now; add an operator reconciliation path before scaling.
6. **High for Sales Navigator-only cutover — Classic routes remain active.** Classic inbound `7o5EBdvwAuIaWW7k` is active and still contains `Send LinkedIn Inbound Message`; the old social outbound router `kqIi8i1RjFAZKrK3` is active and still contains `Route Outbound to Unipile` with LinkedIn references. This audit did not establish whether Classic's external webhook is currently delivering events, but these routes have not been excluded from GHL. The earlier Sales Navigator-only cutover requirement is therefore not yet verified. Review both routes and disable/filter only their Classic LinkedIn branches at cutover while preserving Instagram and historical messages.
